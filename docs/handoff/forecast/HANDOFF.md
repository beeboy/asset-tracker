# 분석 탭 "목표일 전망" 화면 개편 인계

디자인 캔버스: "목표일 전망 개선안" (claude.ai 아티팩트, 보드 "목표일 전망 · 개선안")
같은 폴더의 `Forecast.dc.html`이 확정 목업 원본이다. 마크업, 색, 간격, 문구는 이 파일에서 가져온다.
현재 코드: `ios-app/Naeilo/Views/AnalysisView.swift`의 `ForecastView`(195행 부근), 상태는 `AppModel`의 `lens`, `trust`, `shock`, `monthly`.

## 왜 바꾸나

일반 사용자가 이 화면을 어렵다고 느낀다. 원인은 다음과 같다.

- 같은 목표인데 렌즈 칩에 따라 달성 확률이 19%, 50%, 57%로 바뀐다. 어느 값을 믿어야 하는지 안내가 없다.
- 칩 이름과 내용이 어긋난다. "현재 정세"는 실제로는 장기 평균 회귀(가장 보수적)이고, "과거 추세"는 가장 낙관적이다.
- 통계 용어가 그대로 노출된다. 예: 중앙값, 나쁜 5%, 50%·90% 범위, 3,000갈래 길.
- "목표 달성 확률"과 "한 번이라도 닿을 확률"이 함께 나오는데 차이 설명이 없다.
- 그래프에 Y축 값, 지금 위치, 목표일 표시가 없다.
- 조작 컨트롤(추세 슬라이더, 외부 요인, 월 적립)이 결과보다 한참 아래에 있어서, 바꿔도 변화가 보이지 않는다.
- "웹과 같은 목록", "naeilo.com과 같은 계산"처럼 앱만 쓰는 사람에게는 맥락이 없는 문구가 있다.
- '내 목표' 화면(docs/handoff/HANDOFF.md의 B안)과 역할이 겹쳐 보인다.

### 확정된 방향

- **'목표 판정'은 내 목표 화면이 맡는다.** 판정은 "언제 닿나, 내가 뭘 바꾸면 되나"를 말한다.
- **'전망'은 이 화면이 맡는다.** 이 화면은 "시장이 어떻게 가느냐에 따라 목표일 내 자산이 얼마나 갈리나"를 보여 준다. 목표는 보조선으로만 쓴다.
- **"만약에 매달 더 넣는다면"은 이 화면에서 뺀다.** 납입액은 사용자가 정하는 계획이므로 내 목표 쪽 몫이다. 이 화면에는 내 목표로 가는 링크만 둔다.
- **버튼 3개와 슬라이더 1개는 같은 축이다.** 버튼은 간단히 볼 때, 슬라이더는 정교하게 볼 때 쓴다.

## 화면 구성 (위 → 아래)

1. **상단 바**: 뒤로 버튼, 제목 "목표일 전망".
2. **헤드라인**: "시장이 어떻게 움직이느냐에 따라 / [목표일 연월] 내 자산은 이만큼 달라져요". 판정 문장("가능성 반반" 등)은 넣지 않는다.
3. **시나리오 카드**: 한 카드 안에서 조작과 결과가 같이 보여야 한다. 첫 화면 안에 들어오는 것이 핵심이다.
   1. **세그먼트 버튼 3개**: 신중하게 / 내 설정 / 지난 3년처럼.
   2. **추세 슬라이더**: 항상 보인다.
      - 라벨: "지난 3년 추세를 얼마나 믿나요 · N%"
      - 범위 0~100, 5단위. 아래 눈금 "0% 신중하게 / 50% 반반 / 100% 지난 3년처럼"
      - 버튼과 슬라이더의 연동:
        - '신중하게' → 슬라이더 0%
        - '지난 3년처럼' → 슬라이더 100%
        - '내 설정' → 마지막으로 직접 정한 값(기본 50%)
        - 슬라이더를 0~100 사이로 직접 움직이면 그 값이 '내 설정'으로 기억된다.
        - 0%나 100%에 닿으면 해당 버튼이 선택된다.
   3. **가정 설명 한 줄**: 예) "지난 3년 추세를 50% 믿는다고 볼 때 · 연 +33%"
   4. **큰 숫자**: "가장 그럴듯한 금액" N억 원(목표일 중앙값). 옆에 "지금보다 +N%"를 붙인다(감소면 빨강). 아래에 "10번 중 9번은 [5백분위] ~ [95백분위] 사이".
   5. **범위 차트**:
      - 띠: 50% 띠, 90% 띠, 선택 시나리오의 중앙값 선(진한 초록)
      - 비교선: 다른 두 시나리오의 중앙값 선(회색 점선). 선 끝에 이름표를 단다.
      - 표시: 목표선(주황 점선, 축 라벨 "목표"), 지금 위치 점과 "지금 N억", X축(지금 / 1년 뒤 / 2년 뒤 / 목표일), Y축 눈금(0 / 5억 / 15억)
      - 차트는 카드 너비를 꽉 채운다. 오른쪽 여백을 두지 않는다.
   6. **범례**: 10번 중 5번 / 10번 중 9번 / 다른 시나리오.
   7. **경고**: 연 기대가 30%를 넘을 때만 표시. "연 +N%는 흔치 않은 속도예요. 지난 3년이 유난히 좋았다면 실제로는 이보다 낮을 수 있어요."
4. **"세 가지 미래 한눈에" 표**:
   - 열: 시나리오(연 기대 %) / 그럴듯한 값 / 나쁘면 / 10억 넘을 확률
   - 행: 3개. 행을 누르면 그 시나리오가 선택되고, 선택된 행은 강조한다.
   - 아래 하방 메시지: "어느 시나리오든 운이 나쁘면 지금(N억)보다 줄어들 수 있어요." 이 문장은 실제 값으로 판단해 문구를 고른다(아래 '구현 차이' 참고).
5. **"전망을 흔들 수 있는 일정" 카드**: 기존 "외부 요인 넣기" 토글을 대체한다.
   - 오른쪽: 토글
   - 설명: "켜면 이런 날에 더 크게 흔들린다고 보고 계산해요."
   - 아래: 앞으로 다가올 일정 목록(날짜 + 이름). 예) [보유 종목] 실적 발표, 한국은행 기준금리 결정, 미국 FOMC.
6. **"자세히 보기" 접이식 (기본 접힘)**:
   - "중간에 한 번이라도 10억을 넘을 확률" 어두운 카드(1·2·3년 안 막대). 설명: "잠깐 넘었다가 다시 내려오는 경우도 세요. 그래서 표의 확률보다 높아요."
   - 버튼과 슬라이더 관계 설명 한 줄.
7. **하단 안내**: "예측이 아니라 가능한 범위예요. 지난 3년 움직임을 바탕으로 3,000가지 경우를 계산했어요."
8. **링크**: "납입이나 종목 구성을 바꿔 보려면 내 목표로 →"

### 용어 바꾸기

| 지금 | 바꿀 말 |
|---|---|
| 현재 정세 | 신중하게 |
| 과거 추세 | 지난 3년처럼 |
| 내 관점 | 내 설정 |
| 목표일 중앙값 | 가장 그럴듯한 금액 |
| 나쁜 5% | 운이 나쁘면 / 나쁘면 |
| 50%·90% 범위 | 10번 중 5번 / 10번 중 9번 |
| 목표에 한 번이라도 닿을 확률 | 중간에 한 번이라도 10억을 넘을 확률 |
| 외부 요인 넣기 | 전망을 흔들 수 있는 일정 |
| 3,000갈래 길, naeilo.com과 같은 계산 | 3,000가지 경우를 계산했어요 (웹 언급 삭제) |

## 목업과 실제 구현의 차이

- **숫자는 예시다.** 목업의 계산은 캡처 화면 숫자를 바탕으로 만든 근사식이다. 실제 값은 전부 앱의 몬테카를로 결과(`m.forecast`)에서 받는다.
  - 근사식의 내용: 현재 자산 3.30억은 역산한 값이다. 신중하게 4.74억/1.31억, 지난 3년처럼 11.52억/3.06억은 앱 화면 값이다. 그 사이는 기하 보간했고, 분포는 로그정규로 가정했다.
  - 실제로 받아야 할 값: q5, q50, q95, pGoal, byYear.
- **비교에 세 시나리오 결과가 동시에 필요하다.** 비교선과 표 때문이다. 지금 `Forecast`가 렌즈 셋의 q50, q5, pGoal을 한 번에 주는지 확인해야 한다. `muBase`와 `muTrend`는 이미 있다. 없으면 계산 비용과 캐시 방식을 정해야 한다.
- **슬라이더와 렌즈의 관계를 확인해야 한다.**
  - 지금 코드는 `lens`(.base/.mine/.smooth)와 `trust`가 따로다. 목업은 "신중하게 = trust 0%, 지난 3년처럼 = trust 100%"를 전제한다.
  - 실제 계산에서 `.mine` + trust 0이 `.base`와 같은 값인지, trust 100이 `.smooth`와 같은지 확인한다.
  - 다르다면 버튼과 슬라이더의 연동 방식(같은 축으로 합칠지, 슬라이더는 '내 설정'에서만 쓸지)을 사용자에게 다시 묻는다.
- **기본값이 바뀐다.**
  - 기본 렌즈: 지금 `.mine` → 목업은 '내 설정 50%'로 연다.
  - `trust` 기본 50은 그대로 둔다.
  - '내 설정' 값을 따로 기억하려면 `mineTrust` 같은 상태를 하나 추가해야 할 수 있다.
- **월 적립을 빼는 범위를 정해야 한다.** 이 화면의 UI에서 "매달 더 넣는다면"을 지운다. 다만 `m.monthly`가 다른 화면, 위젯, 웹 동기화에서 쓰이는지 확인한 뒤, 상태를 남길지 지울지 정한다. 남기더라도 이 화면 계산에는 0을 쓸지, 내 목표에서 정한 값을 쓸지 정해야 한다.
- **일정 목록은 새로 만들어야 한다.** 목업의 [날짜], [보유 종목]은 자리 표시다. `shock`가 쓰는 일정 데이터(웹과 같은 목록)에서 앞으로 다가올 3~5건을 꺼내 보여 준다.
- **하방 메시지는 조건부다.** "셋 다 지금보다 줄어들 수 있어요"는 세 시나리오의 q5가 모두 현재 자산보다 낮을 때만 맞다. 실제 값으로 판단해 문구를 고른다.
- **목표가 아닌 모드도 있다.** `isGoal == false`인 "3년 전망"(회복 루트, 본전 기준)은 목업에 없다. 같은 구조에 "목표" 대신 본전을 넣으면 되는지 확인한다.
- **차트를 새로 그려야 한다.** 지금 `FanChart`는 로그 축이고 눈금이 없다. 목업처럼 선형 축, 눈금, 지금 점, 비교선, 이름표를 넣으려면 새 차트가 필요하다. 로그 축을 유지할지는 계획 단계에서 제안한다.
- **결과를 아래로 내린다.** 지금은 결과 영역이 `PinnedLayout`으로 상단에 고정돼 있다. 목업은 버튼, 슬라이더, 결과를 한 카드에 둔다. 고정 영역을 유지할지, 카드째 스크롤할지 정한다(목업은 스크롤).
- **일정 목록은 외부 요인 화면과 겹친다.** 같은 폴더 옆의 `docs/handoff/external-factors/`(외부 요인 개편안)에도 일정 카드가 있다. 두 화면에서 일정 데이터와 카드 모양을 같이 쓸지 계획 단계에서 맞춘다.
- **웹(`web/app.js`의 전망 탭)도 같은 화면이다.** 이번 범위를 iOS만으로 할지, 웹까지 할지는 사용자 결정 대기다.

## 다음 스레드가 할 일

1. 이 문서와 `Forecast.dc.html`을 읽는다. 같은 폴더 위의 `docs/handoff/HANDOFF.md`(내 목표 B안)도 함께 읽고 역할 구분을 확인한다.
2. `ForecastView`, `AppModel`의 forecast 계산(`lens`, `trust`, `shock`, `monthly`), `FanChart`, 웹 전망 탭 코드 위치를 파악한다.
3. 위 '구현 차이' 항목마다 확인 결과와 제안을 적어 구현 계획을 낸다. 계획에는 다음을 담는다.
   - 바꿀 파일
   - 새로 필요한 계산이나 상태
   - 웹과 Swift 사이 계산 일치(parity) 도구에 미치는 영향
   - 빌드와 검사 방법
4. 사용자 승인 전에는 코드를 바꾸지 않는다. 커밋도 하지 않는다.
